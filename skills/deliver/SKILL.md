# deliver

Own closure whenever work finishes, without being asked, so the user can archive the thread; stop only at the approval gate for human-facing communication, with the draft, recipients and evidence already prepared. Work with no owning task, such as personal internal tooling, skips the task record and time steps but still retains its proof, cleans up, and ends with the close-out list; only an answer that created and changed nothing skips closure. Helper calls to `verify`, `artifacts`, or `tasks` return here; do not recursively re-enter delivery.

Get verified work to its audience and reconcile the records that make it usable. Coordinate existing procedures without expanding authority.

1. Read the owning task, project context, accepted outcome, evidence, and current artifact or release. Notion is the default execution and closure record; include an external sync only when the user explicitly requests that destination. A customer’s source link or Project membership alone does not authorize outbound synchronization. Resolve audience, channel, language, and permissions. Ask only for missing facts that change delivery.
2. Use `verify` for required outcomes lacking current proof; reuse valid evidence for the unchanged artifact. Distinguish implementation ready, PR ready, merged, deployed, and production-verified. Close only what the request or task asked for; failed or unverified requirements remain blockers unless the user explicitly accepts a documented exception to that check. Keep the exception and supporting evidence visible rather than describing the check as passed.
3. When a task exists, use `tasks` to link proof, reconcile state, and post a useful result comment directly, as it describes. Without a task, keep the proof in a retained evidence location and name it in the close-out list. Read existing records before retrying to prevent duplicate comments, assets, or time entries. Collect the required artifacts from workers and package the retained baseline and final evidence through `artifacts`: follow its evidence-format rules rather than scattering a larger set across messages. Use nonvisual proof when appropriate. Attach the actual results to the task's completion comment as `tasks` describes, never to the task body or Assets, or link them in the authorized PR destination; verify access and privacy, and obtain approval before posting any other human-facing completion communication. Drafts of reports, documents, and assets stay in the working space (working files, the conversation, or the task's draft comment) until they are approved; only the approved final is attached or linked in Notion, through `documents` when it belongs in Documents. Do not discard evidence during cleanup or present a missing baseline as a before/after comparison.
4. Reconcile actual duration and date under `tasks`. When time is missing, ask with the three suggested durations `tasks` describes and log only what the user picks or types. Reuse matching entries. Required unresolved time prevents Done; repair missing time on completed work without reopening it.
5. Before any human-facing post or send, follow [communication approval](references/communication-approval.md) and the channel's stricter rules. Send through the channel's connector or its matching skill. Prepare one approval bundle containing the complete message, destination, recipients or mentions, and the actual evidence attachments; do not omit the proof and request another round later. Obtain approval, then verify delivery. Internal comments, replies, and mentions also require approval; Notion task comments are the exception and are posted directly through `tasks`. Continue authorized internal work while drafts wait.
6. After meaningful corrections, recurring failures, or costly rework, use `verify` and its correction-routing reference to identify the responsible layer and any durable improvement. Skip routine retrospectives when nothing useful was learned.
7. When recurring work has a stable trigger and repeatable outcome, check for an existing automation and propose the smallest useful addition or improvement. State its trigger, scope, expected benefit, failure handling, and approval gates. Prefer a script or native capability when scheduling adds no value. Do not create or enable an automation without approval, and never use automation to bypass human-communication or other action approvals.
8. Clean up what the work created, whether or not it has a task or anyone asked, and after a failed or blocked attempt too: test sessions and threads, temp files, servers, browsers and other processes, merged branches and worktrees, and unused drafts, including in Shopify Files. Retain the proof first. Keep only what must stay, such as a pull request awaiting review or what the next owner needs to continue, and name it in the close-out list. Ask before deleting anything you did not create. Approved finals go to Notion, with a copy in `~/projects/<project>/sessions/<yyyy-mm-dd>-<session-title>/` and a README linking the session ID, PR, and task.
9. End the reply with the close-out list: a short numbered list of plain sentences, never `Label: value` lines, covering what is done and its proof, the task (or why there is none), the pull request state, what was cleaned up, and what waits on the user or someone else. Say when one has nothing to report rather than leaving it out. The numbers let the user answer item by item.

Before reporting full closure, re-read the required destinations and reconcile task status, accessible evidence, actual time, posted communication, and any explicitly requested external sync as separate items. A successful comment or time entry does not prove the status or attachments persisted. Missing required proof prevents internal completion unless the user accepts a documented exception; pending communication or external publication remains a delivery item, not a false full-closure claim. No external read or write is required solely to close Notion work.

Internal reviewers need readiness and risks; customers need what is available and how to use it. Never announce a PR as live. Report delivered state and any outstanding proof, time, record, or communication. Mention actual time only when useful at closure or requested. Transfer unfinished work with enough evidence to continue, not a false completion claim.
