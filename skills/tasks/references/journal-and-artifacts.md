# Task journal and artifacts

## Task journal and artifacts

Post Notion task comments and replies directly, without separate approval, as the hard rule in this skill says and following the journal procedure below. Any other human-facing communication still needs approval under `deliver` before it is sent or posted. Continue factual internal record and asset maintenance within the authorized scope while such approval is pending.

Use each part of a task for one job. Properties hold operational state, including the mandatory Priority for active work. Assets hold only the inputs the work needs, never outputs. Comments hold progress and results. The body explains the accepted request as work to do, never its results, progress or completion state, even after the work is finished, in two or three short paragraphs followed by useful context bullets in ordinary sentences. Follow the prose rules in records-and-tasks.md. Keep necessary constraints, blockers, and useful links concise, without headings, Done when lists, acceptance checklists, generic steps, speculative requirements, or repeated properties. Update the body when accepted feedback makes it stale.

Comments hold real discussion, feedback, decisions, and delivered results. Do not create a comment merely to archive source history trimmed from the brief or to hold an asset. A specialist’s verified-match comment for explicitly requested cross-system synchronization is the narrow approved exception; do not create it for ordinary source capture. Refer to the client team or project in prose, not individual conversation participants; actual individual owners stay in Owner and Assignee. Preserve an accepted request as work to do, not a transcript or personal attribution.

Record feedback, reviewable revisions, approvals, rejections, corrections, blocker changes, pushes, deployments, and final verification when they matter to someone following the task. Skip repeated handoffs and internal telemetry that changes nothing for the reader. Before posting, fetch the body and discussions and compare the new result with existing commits, approvals, artifacts, and state.

Reply to the discussion that owns the continuing conversation. Start a new page-level discussion only when the subject changes. A local revision and its later approved push may be separate replies when the approval between them matters, but the second reply must add only the new fact. Do not repeat the branch, tests, caveats, and history.

Treat specialist handoffs as internal evidence, not publishable copy. Write fresh prose in the task's language and apply `write`. State what changed, which feedback it addresses, what a teammate can review, and the next real step. Weave useful links into sentences. Keep agent names, command output, raw branch choreography, repeated test counts, and machine-local paths out of the comment. Put detailed QA in an attached report when it remains useful.

Keep the body focused on the accepted current work. Write delivery comments about what was delivered, how to use it, and useful evidence. Leave out problems found and fixed during the work and notes about things outside the task, even when a handoff lists them as incidents or open items. Keep one only when someone still has to act on it, it still affects the result, or the user asks for it. A real follow-up becomes its own task or a line in the report to the user, not a caveat in the body.

Sort every file by its job before uploading it. Inputs the work needs, such as a brief, client files or reference images, go in Assets; use a body attachment only when Assets cannot hold the file. Results go on the comment for the event that produced them, and final results on the completion comment, as [time-and-completion.md](time-and-completion.md) describes. A result file is one a reviewer or the next agent needs to judge, use or reproduce the result: the deliverable, its report, and the evidence it rests on. Code, scripts, configuration and raw data are not result files even when the report names them; they stay in their repository or inside an evidence archive. Never put an output in Assets or the body, and never create a comment just for asset storage. Keep repository commits, pull requests, and other durable source records as links woven into sentences, without Source:, Repository:, or Asset: labels. Turn a local HTML preview, image, video, PDF, archive, or report into a Notion attachment; never leave its local path as the only record. For small text files use the Notion attachment content upload. For local binary files use the Notion local file-upload flow, then attach the resulting upload. Use a direct public URL when it is already durable and needs no headers.

When a local file exceeds the MCP's 20 MiB limit, keep the original at its canonical source and create a review copy below the limit with format-appropriate compression or transcoding. The copy must preserve the text, captions, legibility, behavior, or visual evidence people need to review. Do not overwrite the original or optimize a file that already fits. Use `ntn` only when the exact original must be attached and cannot reasonably fit below the limit. Resolve approved credentials through the current secure environment, and create the attachment or comment with the same Notion integration that uploaded it. Never mix file-upload IDs across integrations.

A Notion comment holds at most three attachments. An event may attach up to nine result files: up to three on its comment, and the rest in at most two replies in the same discussion, each with one short sentence saying what the files are. Attach a deliverable made of several files, such as six images, as separate files so people can open them directly. Past nine files, keep the deliverable itself unzipped and put the supporting files in one zip archive. Attach changed files once; reference the earlier Notion attachment when a later event reuses an unchanged file.

Attach files through Executor's Notion app, with one integration for the whole event. Upload each file with `tools.notion.files.upload`, which returns a `file_upload` ID that stays valid for one hour. Then post with `tools.notion.api.comments.createAComment`, passing up to three of those IDs as `attachments` and `display_name` as `{ type: "custom", custom: { name } }`. Post the remaining files in at most two replies, with `discussion_id` set to the comment's discussion, three files each, and read each result before the next call. If a reply fails, attach only the files still missing in a reply to that discussion; never post the comment again. Through Executor, uploads above about 3 MB can time out inside `execute`, so compress first; a text-heavy evidence folder usually shrinks well as `tar.xz` inside the zip.

Write comments as short paragraphs: a bold first line with the result, then only what the reader needs to act. Notion comments show bold, italic, inline code, links and paragraph breaks, but not numbered lists, bullets or headings, which arrive as plain text; never use them in a comment. In comments and task bodies, write file names, paths and domains as inline code, because Notion turns bare names such as findings.md into links to websites. Prefer several small comments over one dense one, and keep the completion comment as concise as `write` allows.

After writing, fetch the page and affected discussion again. Confirm the body, properties, reply placement, links, and attachments. If the result is uncertain, read current state before retrying. A task journal update is complete only when Notion contains the human explanation and the evidence needed to review it without access to the agent's machine.
